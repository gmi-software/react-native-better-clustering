Headless engine (advanced)

Use the low-level C++ ClusterEngine when you own map rendering and only need cluster computation — for example a custom map SDK or server-side viewport queries in a native module.

Import from /engine:

import {
  createClusterEngine,
  bboxToViewport,
  DEFAULT_SUPERCLUSTER_OPTIONS,
} from 'react-native-better-clustering/engine'
import { packPoints } from 'react-native-better-clustering/utils'

For GeoJSON input and supercluster-compatible helpers, prefer Supercluster (used internally by useClusterer). Reach for createClusterEngine() only when you need direct buffer control.

createClusterEngine(), Supercluster.load() and Supercluster.loadAsync() throw if the native module is missing from the app binary; the error says how to rebuild (see Troubleshooting).

Lifecycle​

Call methods in this order:

  1. setOptions — radius, zoom range, reducers, tile extent, etc.
  2. setPoints — binary buffer from packPoints() (/utils export; must match options).
  3. build() or buildAsync() — build the spatial index.
  4. Query — getClusters, getChildren, getLeaves, getClusterBounds, getClusterExpansionZoom.
  5. dispose() — free the native index when you are done (see Native memory).

setOptions or setPoints clears the index. After either call, isBuilt is false until you run build() again.

const engine = createClusterEngine()

engine.setOptions({
  radius: 40,
  minPoints: 2,
  minZoom: 1,
  maxZoom: 20,
  extent: 512,
  nodeSize: 64,
  reducers: [],
})

const { buffer } = packPoints([
  { latitude: 52.23, longitude: 21.01 },
  { latitude: 52.24, longitude: 21.02 },
])

engine.setPoints(buffer)

if (!engine.isBuilt) {
  await engine.buildAsync() // or engine.build() for small datasets
}

const viewport = bboxToViewport([-180, -90, 180, 90], 10)
const clusters = engine.getClusters(viewport)

getClusters reads the viewport as supercluster reads a bbox: across the antimeridian, pass the longitudes unwrapped (west: 170, east: 190) or wrapped (west: 170, east: -170); a span of 360° or more returns the whole world, with each feature once.

getClusterExpansionZoom(id) returns the first zoom at which the cluster has split into its children, whichever zoom you saw it at, so "zoom to the expansion zoom on press" always reveals the children. It returns maxZoom + 1 for a cluster still there at maxZoom (points at the same coordinate, for example) and for a point id.

getClusterBounds(id) returns the box { north, south, east, west } that every leaf under the cluster spans, without the leaves: four numbers cross into JS for a cluster of 100k points, where getLeaves would convert each point. Fit the map to it on a cluster press. A point id spans its own point. The box uses the coordinates the engine indexed, which clamps latitudes beyond ±85.05° and longitudes beyond ±180°. Supercluster has the same method, returning a [west, south, east, north] bbox, and uses it for a cluster's getExpansionRegion().

Always guard queries with isBuilt when options or points can change between renders:

function queryClusters(engine: ClusterEngine, viewport: Viewport) {
  if (!engine.isBuilt) {
    return []
  }
  return engine.getClusters(viewport)
}

Above maxZoom​

As in supercluster, getClusters floors the zoom and clamps it to minZoom through maxZoom + 1. At maxZoom + 1 and above it returns every point inside the viewport on its own, so points too close to split at maxZoom still come apart at street level, without raising maxZoom (which costs build time and memory). Points at the same coordinate come back as separate points on top of each other. Supercluster.getClustersFromRegion and useClusterer pick a zoom up to maxZoom + 1 too, as react-native-clusterer does; the bundled MapView stops at maxZoom and spreads such clusters out instead.

Threading​

buildAsync() builds on a background thread from the points and options the engine has when you call it. Every method stays safe to call while a build is pending:

  • Queries read one complete index each. While a build is pending they answer from the current index, or throw if isBuilt is false; they never see a half-built one.
  • setPoints and setOptions apply to the next build. They clear isBuilt as usual, and the pending build's index is discarded when it finishes: its promise still resolves, but isBuilt stays false until you build again.
  • Overlapping builds (buildAsync() twice, or build() while buildAsync() is pending) each settle on their own. The first to finish publishes the index; a later one of the same points and options is dropped.
  • dispose(), or dropping the last reference to the engine, is safe mid-build: the pending build frees its index when it finishes (see Native memory).
const pending = engine.buildAsync()
engine.setPoints(nextBuffer) // the pending build is now stale
await pending
engine.isBuilt // false: build again for nextBuffer

Native memory​

The index lives in native memory, which grows with the number of points (the core benchmark puts 100k points spread over the world at about 43 MB). The JS garbage collector does not see that memory, so an engine you drop is freed only when the collector happens to run, and engines discarded on every data refresh can pile up.

Call dispose() when you are done with an engine. It frees the index right away; if a buildAsync() is still running, the index is freed as soon as that build finishes. Any later call on the engine throws, including a second dispose().

The garbage collector learns an engine's native size only when the engine is handed to JS, which happens while it is still empty. After a build resolves, report the real size so the collector counts it:

import { NitroModules } from 'react-native-nitro-modules'

await engine.buildAsync()
NitroModules.updateMemorySize(engine)

Call it after the build resolves, not while one is pending. Supercluster, useClusterer and MapView do both for you: Supercluster.destroy() disposes its engine.

Errors​

Direct ClusterEngine callers get explicit failures instead of silent empty results:

CallConditionResult
setOptionsan option outside its valid valuesthrows, naming the option; the previous options and index stay
setPointsnull / wrong layoutthrows
getClusters, getChildren, getLeaves, getClusterBounds, getClusterExpansionZoomisBuilt === falsethrows
getChildren, getLeaves, getClusterBounds, getClusterExpansionZoomclusterId is not a 32-bit integer (NaN, Infinity, 1.5)throws
getLeavesfractional limit or offset, or NaN offsetthrows
any method or propertyafter dispose()throws

Invalid buffers, invalid numbers and missing build() throw with messages prefixed ClusterEngine:. Use packPoints() for buffers and check isBuilt after reloads.

getLeaves reads a limit of 0, a negative number, Infinity or NaN as no limit, so supercluster's getLeaves(id, Infinity) returns every leaf. A negative offset skips none. For an id that is a whole number but no node, such as -1, getChildren and getLeaves return [] and getClusterBounds returns undefined.
