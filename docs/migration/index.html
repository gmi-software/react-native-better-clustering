Migrating from react-native-map-clustering

The main export is the clustered MapView, with the props and callbacks of react-native-map-clustering 4.0. react-native-better-clustering/compat is a backwards-compatible alias. Change one import:

- import MapView from 'react-native-map-clustering'
+ import MapView from 'react-native-better-clustering'

Your <Marker> children, clustering props and react-native-maps props carry over. Children are picked for clustering by the same rule (see Which children are clustered). Check the differences below, and if you come from 3.x, the onRegionChangeComplete arguments.

Unlike react-native-map-clustering, this package has native code: it needs React Native 0.78+ with the New Architecture, react-native-nitro-modules, and a rebuild of the app (a development build with Expo, not Expo Go). See Platform Setup.

MapView also adds props react-native-map-clustering does not have, such as spiderfyMinZoom, spiderfyMaxLeaves, clusterFadeInDuration, clusterUpdateIntervalMs, clusterRenderMargin and onError. See the MapView API.

Coming from react-native-map-clustering 3.x​

onRegionChangeComplete follows react-native-map-clustering 4.x: it receives (region, details, markers). 3.x passed (region, markers), so a handler written for 3.x now gets the details of react-native-maps where it expects the markers. TypeScript only catches this when the handler's parameters have types. Take the markers from the third argument:

  <MapView
-   onRegionChangeComplete={(region, markers) => setVisible(markers)}
+   onRegionChangeComplete={(region, details, markers) => setVisible(markers)}
  >

In development, MapView warns once when the handler declares exactly two parameters (a parameter with a default value, and every one after it, does not count). A handler that means (region, details) can declare the third parameter, (region, details, _markers) => …, to silence the notice.

superClusterRef​

superClusterRef.current is a Supercluster, not a supercluster instance. It has supercluster's query methods (getClusters, getChildren, getLeaves, getClusterExpansionZoom), but no getTile, and it changes at different times:

  • The index builds on a background thread. Until the first build has loaded, current is null, so check it before you query.
  • When markers are added, removed, moved or reordered, the previous engine keeps serving queries until the new index has loaded. Then current is replaced and the previous engine destroyed, so read superClusterRef.current when you query instead of keeping the instance: a destroyed one throws.
  • With clusteringEnabled={false}, and after the map unmounts, current is null.

Whenever current is not null, it is loaded and ready to query.
